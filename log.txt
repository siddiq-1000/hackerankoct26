## 1. What the task is (ground truth from problem_statement.md)

For each of the 518 rows in `dataset/deletion_requests.csv`
(`case_id,email,requested_at,reported_status,reported_at,audit_at,request_text`) output one row:

`case_id,deletion_status,steps_json` -> `output.csv` in repo root, sorted by `case_id`, header exactly `case_id,deletion_status,steps_json`.

- `deletion_status` in {`COMPLETE`, `INCOMPLETE`, `NOT_APPLICABLE`}.
- `NOT_APPLICABLE` = the person did not actually request deletion. `steps_json` must be `[]`.
- `reported_status` (COMPLETE / PARTIALLY_COMPLETE / NOT_STARTED) is only a **claim**. Truth comes from evidence at `audit_at`.
- A deletion is COMPLETE only if: every relevant copy has the treatment required by `deletion_rules.csv`; no active sync/import/restore path can recreate the data; retained records hold only permitted identifiers; records that must be retained still exist.
- Account **tombstones**: the stable `user_id` may stay, but name, email, phone and email hash must be removed.
- Scope of "copies": databases, replicas (regional / reporting / failover), logs, support attachments, exports, search indexes, archives, backups; plus sync/restore processes that can bring data back.

### Step object (every element of `steps_json`)
```
{"step_no":1,"phase":"FINDING","system_id":"...","resource_id":"...","operation":"...","state":"...","evidence_id":"..."}
```
`step_no` starts at 1, consecutive. `evidence_id` is a `file_id`, `activity_id` or `audit_id`.

### Allowed (phase, operation, state) triples — this is the exact vocabulary and ORDER
| Phase (1st) | Operation order within phase | State |
|---|---|---|
| FINDING | 1 REPORT_REMAINING_RECORD | PRESENT |
| | 2 REPORT_EXPOSED_PII | PRESENT |
| | 3 REPORT_ACTIVE_DATA_FLOW | ACTIVE |
| | 4 REPORT_RESTORE_RISK | ACTIVE |
| REMEDIATION (2nd) | 1 DISABLE_DATA_FLOW | DISABLED |
| | 2 BLOCK_RESTORE | BLOCKED |
| | 3 DELETE_RECORD | ABSENT |
| | 4 REDACT_RECORD | REDACTED |
| | 5 ANONYMIZE_RECORD | ANONYMIZED |
| VERIFICATION (3rd) | 1 VERIFY_RECORD_ABSENT | ABSENT |
| | 2 VERIFY_RECORD_PRESENT | PRESENT |
| | 3 VERIFY_RECORD_REDACTED | REDACTED |
| | 4 VERIFY_RECORD_ANONYMIZED | ANONYMIZED |
| | 5 VERIFY_DATA_FLOW_DISABLED | DISABLED |
| | 6 VERIFY_RESTORE_BLOCKED | BLOCKED |

**Sort key for every step:** `(phase_rank, operation_rank, system_id ascending, resource_id ascending)`. Array order is graded.

### Evidence-id rules
- COMPLETE: only VERIFICATION steps, each citing a real evidence id that proves the current state.
- INCOMPLETE: findings (cite evidence) + full remediation plan + post-remediation verification. Proposed remediation and future verification use `evidence_id: ""`.
- NOT_APPLICABLE: `[]`.

### Scoring dimensions (design for these)
status accuracy, current + historical identity resolution, discovery of remaining data and recreation risks, correct policy application + evidence refs, completeness and order of steps.

## 2. Proposed architecture: deterministic-first, LLM only where needed

Rationale: 518 cases, rule-driven policy, strict ordering, and a mandatory token/cost report. A deterministic pipeline is reproducible, cheap, testable against `sample_output.csv`, and easy to defend in the AI interview. Use an LLM only for the genuinely fuzzy parts, with caching.

```
deletion_requests.csv
      |
 [1] Loader & schema registry
      |
 [2] Intent classifier  --(no deletion requested)--> NOT_APPLICABLE, []
      |
 [3] Identity resolver  (email -> user_id -> all historical emails/phones/hashes/aliases valid for the case)
      |
 [4] Evidence indexer   (SQL snapshots -> SQLite; JSON/log/txt parsed; PDF/image -> text via OCR/vision, cached)
      |
 [5] State reconstructor (resource state AT audit_at, from evidence + system_activity + audit_log)
      |
 [6] Policy engine      (deletion_rules.csv -> required treatment per resource/data category)
      |
 [7] Gap analyzer       (required vs actual -> remaining records, exposed PII, active flows, restore risks)
      |
 [8] Step planner       (findings / remediation / verification, canonical ordering)
      |
 [9] Validator          (schema, vocabulary, ordering, evidence-id existence, consecutive step_no)
      |
 output.csv  +  usage ledger  +  evaluation harness
```

### Module responsibilities
1. **Loader:** typed readers for every CSV; a schema registry printed to `code/docs/schemas.md`. Parse timestamps to timezone-aware datetimes (check whether the data mixes formats/timezones).
2. **Intent classifier:** decide whether `request_text` is a genuine deletion request. Cheap rules first (keywords, negations like "do not delete", "keep my data", "only update my email", access/export requests, cancellation of an earlier request). LLM fallback for ambiguous text, temperature 0, strict JSON output, cached by hash of `request_text`. Validate against the sample set; this is the biggest swing factor because a wrong NOT_APPLICABLE zeroes the row.
3. **Identity resolver:** start from `email` in `user_identities.csv`; follow `user_audit_log.csv` backwards/forwards to collect former emails, phones, email hashes and any user_id merges/renames. Respect time: use identity valid at the relevant time and keep historical ones, since data may sit under an old email. Watch for case/whitespace/plus-address variants and an email that now belongs to a different user_id (collision trap). Output: `IdentitySet{user_id, emails, phones, email_hashes, aliases, audit_ids_used}`.
4. **Evidence indexer:** use `evidence_files.csv` as the manifest (file_id, system, type, path ...). SQL snapshots: load each into its own SQLite DB (keep primary/replica/reporting/failover separate; record `system_id` for each). Search every table/column for the identity set (including hashed email via the same hash function; discover it from data). JSON/log/txt: structured parse and identifier search. PDF/images: extract text (pdftotext first, OCR/vision only if empty) and cache the result on disk.
5. **State reconstructor:** for each resource, determine present/absent/redacted/anonymized AT `audit_at`. Ignore anything after `audit_at`. Use `system_activity.csv` to find: deletion jobs (and whether they really succeeded), sync/import jobs still enabled, restores, backups taken before vs after deletion, re-indexing, exports. Treat "job reported success" as a claim and cross-check with the data.
6. **Policy engine:** turn `deletion_rules.csv` into a data structure keyed by data category/system. Treatments will be some of delete / redact / anonymize / retain (with permitted retained fields). Apply to every record found, including tombstones, flows and restore sources.
7. **Gap analyzer:** emit typed findings: remaining record, exposed PII (retained record with forbidden identifiers), active data flow, restore risk. Also flag retained records that are missing (policy says retain, but gone).
8. **Step planner:** findings -> remediation -> verification, generated by templates from the gap list; canonical sort. Verification mirrors remediation (DELETE -> VERIFY_ABSENT, REDACT -> VERIFY_REDACTED, etc.), plus VERIFY_RECORD_PRESENT for must-retain records, VERIFY_DATA_FLOW_DISABLED, VERIFY_RESTORE_BLOCKED.
9. **Validator:** hard-fail on any invalid triple, bad order, missing evidence id (for findings and COMPLETE verification), non-consecutive step_no, duplicate steps.

### Cross-cutting
- **LLM client wrapper** logging every call (provider, model, input/output tokens, case_id, purpose) to a usage ledger -> feeds `usage_report.md`. Disk cache keyed by prompt hash so reruns are free and the "final run" numbers are honest.
- **Determinism:** same input -> same `output.csv`. Fixed sort, temperature 0, cached LLM responses.
- **Prompts** live in `code/prompts/*.md`, not inline strings.
- **Config** in `code/config.py` / env vars; no secrets in files.

### Proposed layout
```
README.md
code/
  main.py                  # python3 code/main.py -> ../output.csv
  config.py
  loaders.py  intent.py  identity.py  evidence/ (sql.py, docs.py, ocr.py)
  state.py  policy.py  gaps.py  planner.py  validate.py  llm.py  usage.py
  prompts/
  docs/ (schemas.md, architecture.md, assumptions.md)
  evaluation/
    main.py                # scorer vs sample_output.csv
    evaluation_report.md   # REQUIRED
    usage_report.md        # REQUIRED
    custom_cases/          # >=3 self-made cases, described in the report too
```
